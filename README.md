# Архитектура маркетплейса

Проект архитектуры маркетплейса и заготовка сервиса Orders на Go. Реализован только `GET /health`; бизнес-функциональности нет.

## Домены и распределение по сервисам

| Домен → сервис | Ответственность и причина выделения | Собственные данные |
| --- | --- | --- |
| Пользователи → Users | Профили, роли, контакты и интересы; единый источник сведений о пользователе | `user_id`, профиль, роли, email, предпочтения |
| Каталог → Catalog | Управление товарами продавцов; каталог изменяется независимо от оформления заказов | `product_id`, `seller_id`, карточка товара, категория, цена, валюта, доступность |
| Лента → Feed | Подбор и ранжирование товаров; алгоритм выдачи можно менять и масштабировать отдельно | Постоянных данных нет; получает интересы из Users и товары из Catalog |
| Заказы → Orders | Оформление заказа и управление его статусом; история покупки сохраняется независимо от изменений каталога | `order_id`, `buyer_id`, позиции со снимками названий и цен, количество, валюта, `payment_id`, статус и история |
| Платежи → Payments | Расчёт суммы и учёт платежей; отдельная ответственность за финансовые данные и работу с платёжным провайдером | `payment_id`, `order_id`, сумма, валюта, попытки оплаты, статусы, идентификаторы операций провайдера |
| Уведомления → Notifications | Отправка уведомлений о статусах заказов; доставка сообщений обрабатывается отдельно от оформления заказа | Задания на отправку, адрес получателя, попытки и результаты отправки |

Персонализация ленты основана на выбранных пользователем категориях: Feed ставит подходящие товары выше остальных. Без выбранных интересов товары сортируются по новизне.

## Владение данными

У Users, Catalog, Orders, Payments и Notifications отдельные базы PostgreSQL. Каждый сервис читает и изменяет только свою базу; общих таблиц и доступа к чужим базам нет. Feed собственной базы не имеет.

Catalog хранит текущие цены товаров, Orders — снимки названий и цен на момент оформления заказа. Payments рассчитывает сумму по этим снимкам и хранит статус платежа. Orders хранит статус заказа.

Взаимодействия сервисов и их способ (`sync` / `async`) показаны на C4-диаграмме.

## Альтернативные варианты декомпозиции

**Вариант 1 — модульный монолит.** Users, Catalog, Feed, Orders, Payments и Notifications — модули одного приложения. Каждый модуль отвечает за свой домен и таблицы в одной базе. Модули взаимодействуют вызовами внутри процесса; приложение собирается, выпускается и масштабируется целиком.

**Вариант 2 — шесть микросервисов.** Те же домены распределены по отдельным приложениям. У каждого сервиса с постоянными данными своя база, у Feed базы нет. Сервисы взаимодействуют через API и очереди, выпускаются и масштабируются отдельно.

Варианты отличаются границами приложений и хранения данных, способом взаимодействия и единицей развёртывания.

## Плюсы, минусы и компромиссы вариантов

| Вариант | Плюсы | Минусы | Компромисс |
| --- | --- | --- | --- |
| Модульный монолит | Одно приложение для запуска и сопровождения; вызовы между модулями без сети; изменения данных можно объединить в одну транзакцию | Изменение Feed требует выпуска всего приложения; при росте нагрузки на ленту масштабируется всё приложение | Упрощаем запуск и обмен данными, но отказываемся от отдельного выпуска и масштабирования доменов |
| Шесть микросервисов | Feed можно выпускать и масштабировать отдельно; базы закреплены за владельцами; обработка уведомлений отделена от обработки заказов | Нужно сопровождать несколько приложений и очереди; вызовы по сети могут завершаться ошибкой; изменения в разных базах не объединяются одной транзакцией | Получаем независимость сервисов и хранения данных, но усложняем развёртывание и межсервисный обмен |

## Обоснование финального выбора

**Выбран вариант 2 — шесть микросервисов.**

- Функции кейса образуют отдельные зоны ответственности: пользователи, каталог, персональная лента, заказы, платежи и уведомления. Для каждой выделен свой сервис.
- Степень персонализации определяется самостоятельно: отдельный Feed позволяет менять алгоритм выдачи без выпуска сервисов заказов и платежей.
- Уведомления о статусах заказов обрабатываются отдельным сервисом через очередь, поэтому отправка письма не задерживает ответ на запрос оформления заказа.
- Отдельные базы явно задают владельцев данных и выполняют требование об отсутствии разделяемых баз между сервисами.

Этот выбор принимает дополнительную сложность развёртывания и обмена данными ради независимости доменов. Он не опирается на предположение о высокой нагрузке: такие требования в кейсе не заданы.

Ограничение реализации соблюдено: вся система представлена архитектурой, а в Docker запускается только заготовка Orders с `/health`, без бизнес-логики.

## Запуск в Docker

Требования: установленный и запущенный Docker, свободный порт 8080. Команды выполняются из корня репозитория.

Собрать образ:

```sh
docker build -t marketplace-orders:local .
```

Запустить сервис:

```sh
docker run --detach --rm --name marketplace-orders -p 127.0.0.1:8080:8080 marketplace-orders:local
```

Проверить health-check:

```sh
curl --fail -i http://127.0.0.1:8080/health
```

Ожидаемый ответ: `200 OK`, тело `ok`.

Остановить сервис:

```sh
docker stop marketplace-orders
```
