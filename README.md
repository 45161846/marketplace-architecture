# Архитектура маркетплейса

Учебный проект: проектирование маркетплейса, C4 Container диаграмма и минимальная заготовка одного сервиса в Docker. Бизнес-функциональность не реализуется.

## Текущее состояние

- Выбрана микросервисная архитектура из шести сервисов.
- Описаны домены, владение данными, взаимодействия и альтернативы.
- Добавлена C4 Container диаграмма.
- Добавлена минимальная заготовка Orders на Go с `GET /health` и инструкция локального запуска.
- Проверены локальная сборка и запуск: `GET /health` возвращает `200 OK` и тело `ok`.
- Добавлены Dockerfile, `.dockerignore` и инструкция сборки и запуска контейнера.
- Проверены сборка образа и запуск Orders в Docker: `GET /health` возвращает `200 OK` и тело `ok`.
- Репозиторий локальный, без привязки к GitHub или GitLab.

Диаграмма описывает проектируемую систему. Сейчас реализована только заготовка Orders с health-check: базы, очереди, клиент, внешние интеграции и бизнес-операции сервисов не реализованы.

## Требования и допущения

Маркетплейс должен обеспечивать персональную ленту товаров, управление каталогом продавцов и пользователями, оформление заказов, расчёт и учёт платежей, уведомления о статусах заказов.

Для первой версии архитектуры приняты следующие допущения:

- Пользователь может иметь роли покупателя и продавца. Доступ к операциям и владение товаром проверяет сервис, обрабатывающий операцию.
- Один веб-клиент предоставляет интерфейсы обеим ролям. Конкретный UI-фреймворк не выбран; его реализация не входит в задание.
- Покупатель выбирает интересующие категории. Feed ставит подходящие товары выше остальных; при отсутствии интересов использует общий порядок по новизне. Обучение моделей и история кликов не нужны.
- Catalog хранит текущую цену и признак доступности товара. Резервирование складских остатков не проектируется в этой версии.
- Заказ содержит товары в одной валюте. Payments считает сумму как сумму произведений зафиксированной цены на количество. Доставка, скидки, комиссии, возвраты и выплаты продавцам за рамками этой версии.
- Уведомления направляются покупателю по email. Приём запроса email-провайдером ещё не означает доставку письма; эти результаты учитываются раздельно.
- Нагрузка, состав команды и требования к доступности в задании не определены. Выбор микросервисов не основан на предположении о доказанной высокой нагрузке.

## Домены и распределение по сервисам

| Домен → сервис | Ответственность и причина выделения | Собственные данные |
| --- | --- | --- |
| Пользователи → Users | Профили, роли, контакты и интересы; единый источник сведений о пользователе | `user_id`, профиль, роли, email, предпочтения |
| Каталог → Catalog | Товары продавцов, категории, текущие цены и доступность; независимый цикл изменений каталога | `product_id`, `seller_id`, карточка товара, категория, цена, валюта, доступность |
| Лента → Feed | Подбор и ранжирование товаров; алгоритм выдачи можно менять и масштабировать отдельно от редактирования каталога | На первом этапе постоянных данных нет; получает данные через API Users и Catalog |
| Заказы → Orders | Фиксация заказа и его жизненный цикл; хранит историю покупки независимо от дальнейших правок каталога | `order_id`, `buyer_id`, позиции со снимками названий и цен, количество, валюта, `payment_id`, статус и история |
| Платежи → Payments | Расчёт суммы, попытки оплаты и взаимодействие с платёжным провайдером; финансовые статусы имеют отдельные правила обработки | `payment_id`, `order_id`, сумма, валюта, попытки, статусы, идентификаторы операций провайдера |
| Уведомления → Notifications | Подготовка, отправка и повторные попытки доставки; недоступность email-провайдера не должна блокировать обработку заказа | Идентификаторы обработанных событий, задания, канал, снимок адреса получателя, попытки и результаты отправки |

Отдельный сервис для каждого домена делает ответственность явной. Feed и Notifications выделены, поскольку выдача и доставка сообщений имеют другие режимы работы, чем оформление заказа. Это также увеличивает число развёртываемых приложений — осознанная цена выбранного разбиения.

## Владение данными

У Users, Catalog, Orders, Payments и Notifications отдельные базы PostgreSQL и отдельные права доступа. Каждый сервис читает и изменяет только свою базу. Feed не требует базы для выбранного способа персонализации.

Взаимные SQL-запросы, общие таблицы и межсервисные внешние ключи запрещены. Идентификаторы чужих сущностей служат ссылками на них, но не дают доступа к чужой базе.

Catalog владеет текущей ценой товара. Orders хранит неизменяемый снимок цены и названия на момент оформления — изменение карточки не меняет существующий заказ. Payments владеет суммой и финансовым статусом платежа, вычисляя сумму из переданного Orders снимка. Он не запрашивает текущую цену у Catalog. Orders владеет статусом заказа и обновляет его по результату платежа; статус платежа принадлежит Payments.

Общих транзакций между сервисами нет. Отдельные базы на диаграмме показывают границы владения; размещение баз на физических серверах относится к проектированию развёртывания.

## Технологические решения

| Элемент | Технология | Обоснование |
| --- | --- | --- |
| Серверные сервисы | Go, HTTP API с JSON | Один стек; для заготовки HTTP-сервера достаточно стандартной библиотеки |
| Хранилища | PostgreSQL, отдельная база каждого владельца | Структурированные данные, локальные транзакции и явное разделение доступа |
| Обмен событиями | RabbitMQ, AMQP | Очереди отделяют обработку платежных результатов и уведомлений от отправителя |
| Веб-клиент | JavaScript в браузере | Единая точка взаимодействия покупателя и продавца |
| Заготовка сервиса | Docker | Воспроизводимый запуск одного приложения для проверки задания |

Планируемые PostgreSQL и RabbitMQ не нужны для будущей заготовки, отвечающей только на `/health`. На этапе сдачи запускается один сервис, а остальные части остаются архитектурным проектом.

## Взаимодействия

`sync` означает, что вызывающая сторона ждёт ответ. `async` означает, что результат обрабатывается отдельно от исходного запроса. Асинхронность относится к способу взаимодействия: webhook передаётся по HTTP, но приходит позднее исходного запроса на оплату.

| Отправитель → получатель | Назначение | Способ |
| --- | --- | --- |
| Покупатель / продавец → веб-клиент | Работа с интерфейсом | HTTPS |
| Веб-клиент → Users | Профиль и предпочтения | sync, HTTPS/JSON |
| Веб-клиент → Catalog | Просмотр товаров; управление собственными товарами продавца | sync, HTTPS/JSON |
| Веб-клиент → Feed | Персональная лента | sync, HTTPS/JSON |
| Веб-клиент → Orders | Создание и просмотр своих заказов | sync, HTTPS/JSON |
| Feed → Users | Получение категорий интересов | sync, HTTP/JSON |
| Feed → Catalog | Получение товаров для ранжирования | sync, HTTP/JSON |
| Orders → Catalog | Проверка товаров, получение цен и доступности | sync, HTTP/JSON |
| Orders → Payments | Создание платежа по снимку заказа | sync, HTTP/JSON |
| Payments → платёжный провайдер | Инициирование оплаты | sync, HTTPS/JSON |
| Платёжный провайдер → Payments | Результат операции | async, HTTPS webhook |
| Payments → очередь `payment-results` → Orders | `PaymentSucceeded` или `PaymentFailed` | async, RabbitMQ/AMQP |
| Orders → очередь `order-status-changes` → Notifications | `OrderStatusChanged` | async, RabbitMQ/AMQP |
| Notifications → Users | Получение email покупателя | sync, HTTP/JSON |
| Notifications → email-провайдер | Запрос отправки уведомления | sync, HTTPS/JSON |
| Email-провайдер → покупатель | Доставка сообщения | email |
| Каждый сервис с базой → собственная база | Чтение и запись собственных данных | SQL через протокол PostgreSQL |

Брокер — транспорт событий, а не общая база бизнес-данных. На C4-диаграмме показаны две конкретные очереди RabbitMQ. Payments определяет контракт результатов платежей; Orders — контракт изменений заказов. Подписчик обрабатывает предназначенную ему очередь.

## Сценарий оформления заказа

1. Покупатель отправляет выбранные товары и количество в Orders через веб-клиент.
2. Orders проверяет товары через Catalog и сохраняет заказ со снимком позиций в состоянии `awaiting_payment`. Это локальная транзакция Orders.
3. Orders запрашивает создание платежа у Payments, передавая идентификатор заказа и зафиксированные позиции. Payments рассчитывает сумму, сохраняет платёж и обращается к провайдеру. Клиент получает через Orders ссылку на оплату, если она требуется провайдером.
4. При получении подтверждённого результата провайдера Payments обновляет платёж и публикует событие с `event_id`, `order_id`, `payment_id` и результатом.
5. Orders сопоставляет результат с платежом заказа, обновляет заказ в `paid` либо `payment_failed` и публикует `OrderStatusChanged` с идентификатором события, заказа, покупателя и новым статусом.
6. Notifications получает событие, запрашивает email в Users, сохраняет задание и обращается к email-провайдеру.

Это описание предполагаемого поведения, а не реализованный сценарий.

## Сбои и согласованность

- Между успешной оплатой и обработкой события заказ временно может оставаться в `awaiting_payment`. Это допустимая задержка согласования; единой транзакции заказа и платежа нет.
- Тайм-аут запроса не доказывает, что операция не выполнилась. Повтор создания платежа использует тот же ключ идемпотентности, привязанный к заказу. Payments возвращает существующий платёж; поддержка ключа провайдером должна быть проверена при реальной интеграции.
- Для разрыва между записью в базу и публикацией события предусмотрен transactional outbox: бизнес-изменение и запись события сохраняются одной локальной транзакцией, отдельный отправитель повторяет публикацию до подтверждения брокера.
- Очереди и сообщения должны быть устойчивыми к перезапуску. Подтверждение публикации и подтверждение обработки уменьшают риск потери события, но не исключают дубликаты.
- Потребители учитывают `event_id` в своей базе. Изменение заказа и отметка обработки события выполняются одной транзакцией. Позднее или повторное событие не должно переводить уже оплаченный заказ обратно в состояние ошибки.
- Notifications сохраняет задание до подтверждения обработки события и повторяет неудачные отправки. Защита от повторного письма после тайм-аута требует поддержки идемпотентности со стороны email-провайдера; без неё гарантировать однократную доставку нельзя.
- Webhook проверяется по механизму подтверждения подлинности провайдера; финансовый статус не берётся из заявления браузера об успешной оплате.

Эти механизмы фиксируются как архитектурные решения. В рамках задания они не реализуются.

## Альтернативы и финальный выбор

| Вариант | Плюсы | Минусы и конкретный компромисс |
| --- | --- | --- |
| Модульный монолит: одно приложение, шесть модулей, одна база с таблицами каждого модуля | Простой запуск и сопровождение; внутренние вызовы; локальные транзакции между модулями | Общий выпуск и масштабирование; границы доступа к таблицам необходимо поддерживать внутри кода. Простота эксплуатации достигается ценой независимости частей |
| Шесть микросервисов с отдельными хранилищами | Явные владельцы данных; независимые выпуски; отдельное масштабирование ленты; уведомления обрабатываются независимо от заказа | Сетевые сбои, повторы, задержка согласования и больше инфраструктуры. Независимость частей достигается ценой сложности взаимодействий |

**Выбран второй вариант — шесть микросервисов.** Требования кейса дают различимые зоны ответственности: каталог изменяется продавцами, лента подбирает товары, заказы фиксируют покупку, платежи учитывают деньги, уведомления доставляют сообщения. Выбранное разбиение явно показывает владельцев данных и способы взаимодействия и соответствует выбранному для учебной работы микросервисному подходу.

Ограничение задания соблюдается: проектируется вся система, но реализуется только заготовка одного сервиса. Для небольшого продукта с одной командой модульный монолит мог бы быть более экономичным стартом; сведений о нагрузке для доказательства необходимости микросервисов здесь нет.

## C4 Container диаграмма

Готовая диаграмма для просмотра: [docs/c4-container.svg](docs/c4-container.svg). Отрисовка проверена в браузере.

Источник диаграммы: [docs/c4-container.mmd](docs/c4-container.mmd). Ниже встроена та же схема в Mermaid. Используется нотация блоков и стрелок C4 с автоматическим расположением Mermaid flowchart.

Легенда:

- Тёмно-синие блоки `Person` — люди; серые `External Software System` — внешние системы.
- Синие блоки `Container` — приложения, очереди и хранилища внутри маркетплейса. Для каждого указаны технология и ответственность; цилиндр обозначает базу.
- Сплошные стрелки между приложениями с подписью `sync` — синхронные вызовы. Пунктирные стрелки с подписью `async` — асинхронные взаимодействия: сообщения через очереди и webhook от платёжного провайдера.
- Подписи взаимодействий описывают действие отправителя или вызывающего приложения. Связи приложения с собственной базой оставлены без подписей: приложение читает и записывает только свою базу.
- Протоколы вынесены из стрелок: API клиента — HTTPS/JSON; внутренние API — HTTP/JSON; доступ к базам — SQL через протокол PostgreSQL; очереди RabbitMQ — AMQP; API внешних провайдеров и webhook — HTTPS; доставка письма покупателю — email. Назначение каждой связи приведено в таблице «Взаимодействия».
- Это упрощённая нотация C4 Container для обзорной схемы. Официальные рекомендации C4 предлагают подписывать каждую связь её назначением и протоколом; в этой версии назначение взаимодействий подписано на стрелках, протоколы перенесены в легенду и таблицу, а связи с собственной базой оставлены без подписи, чтобы сократить повторяющийся текст.
- Стрелки API направлены от вызывающего к вызываемому; возврат ответа подразумевается. Для событий показано направление доставки сообщения.
- Рамка — граница маркетплейса. Она не обозначает один процесс или один Docker-контейнер.

## Локальный запуск Orders

Требования: Go 1.26 или новее; свободный порт 8080. Внешние библиотеки, база данных и брокер для заготовки не нужны.

Из корня репозитория:

```sh
go run ./services/orders
```

Сервис принимает HTTP-запросы на порту 8080. В другом терминале:

```sh
curl -i http://localhost:8080/health
```

Ожидаемый ответ: статус `200 OK`, `Content-Type: text/plain; charset=utf-8` и тело `ok` с переводом строки. Остановить сервис можно сочетанием `Ctrl+C` в терминале запуска.

Альтернатива — собрать отдельный исполняемый файл и запустить его:

```sh
go build -o bin/orders ./services/orders
./bin/orders
```

### Устройство заготовки

- `go.mod` задаёт имя модуля и минимальную версию Go.
- `services/orders/main.go` — точка входа Orders. `http.ServeMux` связывает `GET /health` с обработчиком `health`.
- `http.Server` слушает порт 8080 на доступных сетевых интерфейсах; это позволяет позднее запустить тот же код в Docker. `ReadHeaderTimeout` ограничивает время чтения заголовков запроса.
- `health` выставляет тип текстового ответа, статус `http.StatusOK` (200) и тело `ok`.

Проверка `/health` подтверждает, что HTTP-сервер работает и отвечает. Она не проверяет бизнес-функциональность Orders, PostgreSQL или RabbitMQ.

Локально проверено на Go 1.26.8:

- Сборка исполняемого файла и запуск сервера.
- `GET /health` → `200 OK`, текстовый ответ `ok` с переводом строки.
- `GET /orders` → `404 Not Found`: бизнес-обработчик не добавлен.
- `POST /health` → `405 Method Not Allowed`.

После проверки сервер остановлен. Эти результаты относятся к локальному запуску исполняемого файла; результаты отдельной проверки Docker приведены ниже.

## Запуск Orders в Docker

Требования: установленный и запущенный Docker, свободный порт 8080, доступ к реестру образов для первой загрузки `golang:1.26.8`. Локальная установка Go для этого способа не требуется: программа компилируется внутри стадии сборки.

Если Docker Desktop только что установлен, откройте новый терминал, чтобы применилось добавление Docker CLI в `PATH`.

Проверьте доступность Docker: `docker version` должен показать информацию о клиенте и сервере Docker.

Из корня репозитория соберите образ:

```sh
docker build -t marketplace-orders:local .
```

Запустите контейнер:

```sh
docker run --detach --rm --name marketplace-orders -p 127.0.0.1:8080:8080 marketplace-orders:local
```

`--detach` запускает контейнер в фоне. `--rm` удаляет этот контейнер после остановки. `--name` задаёт имя для просмотра логов и остановки. `-p 127.0.0.1:8080:8080` связывает порт 8080 локального компьютера с портом 8080 контейнера; доступ с компьютера — через `localhost`.

Проверьте HTTP-ответ сервиса:

```sh
curl --fail -i http://127.0.0.1:8080/health
```

Ожидается `200 OK` и текстовое тело `ok` с переводом строки. Health-check здесь — HTTP endpoint приложения. Отдельная инструкция Docker `HEALTHCHECK` не добавлена и заданием не требуется.

Для просмотра состояния и логов:

```sh
docker ps --filter name=marketplace-orders
docker logs marketplace-orders
```

Остановите созданный контейнер:

```sh
docker stop marketplace-orders
```

Образ `marketplace-orders:local` остаётся доступным для повторного запуска.

### Как работает Dockerfile

**Образ** — собранный шаблон с файлами приложения и параметрами запуска. **Контейнер** — запущенный экземпляр образа. Dockerfile описывает сборку образа; `docker run` создаёт и запускает контейнер.

1. `FROM golang:1.26.8 AS build` начинает стадию с компилятором Go. `WORKDIR /src` задаёт рабочую папку внутри неё.
2. `COPY` переносит файл модуля и исходный код Orders. Локальный исполняемый файл из `bin/` не используется.
3. `RUN` компилирует программу для Linux. `CGO_ENABLED=0` отключает зависимость от C-библиотек для этой заготовки; `-trimpath` убирает пути сборки из исполняемого файла.
4. `FROM scratch` начинает финальную стадию с пустой основой. `COPY --from=build` переносит только готовый `/orders`: исходники и компилятор остаются в стадии сборки.
5. `USER 10001:10001` запускает процесс с обычным числовым идентификатором пользователя и группы.
6. `EXPOSE 8080` сообщает о порте приложения. Он не публикует порт на компьютере — для этого используется `-p` при запуске контейнера.
7. `ENTRYPOINT ["/orders"]` задаёт программу, которая запускается при старте контейнера.

`.dockerignore` исключает из контекста сборки историю Git, локальные исполняемые файлы, диаграммы и файлы редакторов. Docker Compose не нужен для запуска единственного сервиса.

### Статус проверки Docker

Проверено 2026-10-02 на macOS с Apple Silicon, Docker Desktop 4.93.0 и Docker Engine 29.8.1:

- `docker build -t marketplace-orders:local .` успешно собрал образ из текущего Dockerfile.
- Финальный образ имеет платформу `linux/arm64`, команду запуска `/orders` и пользователя `10001:10001`.
- Контейнер успешно запущен с публикацией порта `127.0.0.1:8080:8080`.
- Реальный `GET /health` через опубликованный порт вернул `200 OK`, `Content-Type: text/plain; charset=utf-8` и тело `ok` с переводом строки.
- `GET /orders` вернул `404 Not Found`, `POST /health` — `405 Method Not Allowed`.
- Тестовый контейнер остановлен и удалён благодаря `--rm`; образ `marketplace-orders:local` сохранён для повторного запуска. Docker Desktop остаётся запущенным.

Проверка выполнена на Linux ARM64 внутри Docker. Сборка и запуск для AMD64 отдельно не проверялись.
